## Critical bugs

### CB-1 — `pairs/scripts/run_walkforward.py` aggregates pair returns with a fixed divisor that under-weights active pairs on partial days
- File: `apps/pairs/scripts/run_walkforward.py:190-195`
- What's wrong: aggregate stream is `sum_over_pairs( pair_ret.reindex(val_dates).fillna(0.0) ) / N_pairs`. Pairs that have no quote on a given date contribute exactly 0 to the numerator while the divisor stays at `N_pairs`. On dates where only a subset of pairs has a return, this systematically biases the aggregate toward zero (under-weights the active pairs by `N_active / N_pairs`).
- Why it matters: that aggregate stream is what `dca-returns.npz` analog `pairs-returns.npz` ships into the DSR aggregator (`apps/docs/scripts/compute_dsr.py`). The published pairs Sharpe is therefore a lower-bound estimate, not the "1/N over active pairs" book the docstring implies. Effect is small on long-quote-overlap pairs and large on pairs with gappy histories.
- Suggested fix: track `active_per_date = sum_over_pairs( pair_ret.notna() )` and divide by `max(active_per_date, 1)`, or equivalently use `pd.concat(..., axis=1).mean(axis=1, skipna=True).fillna(0)`.
- Severity: **3**.
- Confidence: read-the-code certain.

### CB-2 — `ss_portfolio.metrics.cagr` returns NaN/complex on catastrophic losses without raising
- File: `packages/portfolio/src/ss_portfolio/metrics.py:29-36`
- What's wrong: `growth = np.prod(1.0 + r)` can be ≤0 if any compounded return wipes out equity (any `r <= -1.0`). `growth ** (1.0 / years)` on a negative base in float yields NaN. The function then returns NaN silently with no error.
- Why it matters: any walk-forward run that drops below zero equity (e.g. unbounded leveraged short stream, mis-specified test) yields NaN CAGR and infects downstream `calmar` (also NaN). Looks like "no data" rather than "blew up".
- Suggested fix: guard `if growth <= 0: return -1.0` (or raise) explicitly; alternatively work in log space (`np.log1p(r).sum() / years`).
- Severity: **2** (won't fire in current strategies; trivially fires in stress tests).
- Confidence: read-the-code certain.

### CB-3 — `factor.objectives.block_sharpe` charges full one-sided entry cost on every walk-forward val slice, understating val Sharpe
- File: `apps/factor/src/factor/objectives.py:470-473` (and numpy mirror lines 636-638)
- What's wrong: `init_cost = w[0].abs().sum()` is a one-time setup-from-cash cost. In the walk-forward harness (`train_walkforward.py:481-486`), the same function is called on the *val slice*, where `w[0]` represents the first val rebalance — but in a real deployment the portfolio at that point is the *last train weight*, not cash. So val_sharpe is computed as if the portfolio were liquidated to cash at the train/val boundary and re-entered, paying an extra ~10 bps (at default `commission_bps=10`) charged once.
- Why it matters: every published factor val-Sharpe number is slightly understated; the bias is uniform across runs so the *ranking* is intact, but the **DSR ladder** also consumes the per-block stream from `block_port_returns_np` which carries the same spurious entry cost. The `compute_dsr.py` ranking is therefore comparing arcs that all under-report Sharpe by O(comm_bps/sqrt(n_blocks)) annualized — small but systematic.
- Suggested fix: have walk-forward call a no-entry-cost variant for val streams, or carry the previous-window's final weights into the next window's `init_cost` calculation.
- Severity: **2** (bias is bounded by `commission_bps / n_val_blocks`).
- Confidence: read-the-code certain.

### CB-4 — `apply_position_cap` uniform-degenerate path inflates total exposure to 1.0 even when input mass is <1
- File: `packages/portfolio/src/ss_portfolio/weights.py:78-81`
- What's wrong: when `n_nonzero * max_position < 1.0`, the function distributes weight `1/n_nonzero` to every nonzero name — producing a Series that sums to 1.0 regardless of the input sum. If a strategy intentionally runs <100% gross (e.g. risk-rail pre-trims, mixed cash + position), the cap step silently re-inflates to full exposure.
- Why it matters: `regime.live` and `relational.live` both rely on this. If the strategy's `target_weights` sums to <1 (e.g. spread-gating dropped half the universe), the live path will rebalance to a fully-allocated book that the operator never intended. Risk-rail bypass that looks innocent in the rail logic.
- Suggested fix: distribute uniformly subject to a `max_position` ceiling AND preserve `min(1.0, input_sum)` total mass; or document that the cap is also a "fill to 100%" step (in which case the docstring should be explicit about it).
- Severity: **3** for live; **1** for offline.
- Confidence: read-the-code certain.

### CB-5 — `gate.aggregate.build_aggregate_features` breadth feature uses all-time max — soft look-ahead
- File: `apps/gate/src/gate/aggregate.py:145`
- What's wrong: `n_max = float(np.max(agg.n_active_per_date))` is taken over the entire panel and used to normalize the `breadth` feature for *every* row. A 1990 row therefore has its `breadth` value scaled by a 2025-era universe count it could not have known.
- Why it matters: the gate predictor sees a feature whose scale depends on the future. The walk-forward harness picks the same `n_max` across windows; the feature is not exactly "constant per window" — but it's mis-scaled in a way that conflates dates from different universe sizes. Affects gate val R²/Pearson r calibration.
- Suggested fix: track running `max(n_active_per_date[:t+1])` (expanding window) or normalize against the universe count at the train window's end (window-local, not panel-global).
- Severity: **2** (the gate arc is `partial-OOS`; this is one of several reasons the val signal is weak).
- Confidence: read-the-code certain.

### CB-6 — `ss_wavelets.precompute_windows` per-ticker mean normalization uses all-time data
- File: `packages/wavelets/src/ss_wavelets/windowing.py:48-53`
- What's wrong: `pm = power.mean(axis=(0, 1), keepdims=True)` — the divisor is the per-ticker mean over **all dates and all scales**, applied to every output row. Acknowledged in the in-code `TODO(review #10)` comment as safe-only-because the active divergence is scale-invariant.
- Why it matters: if a future caller plugs in a non-scale-invariant divergence (e.g. cosine on un-renormalized power, L2-distance, or *any new* divergence) they will silently leak future power-magnitude into past rows. The guardrail is documentation, not code.
- Suggested fix: take the asserted-divergence list from the docstring and turn it into an `if divergence not in {...}: raise ValueError`. Or expose a `causal_normalize: bool` switch and a rolling-mean alternative.
- Severity: **2** today; **4** if a new divergence lands without the author re-reading this docstring.
- Confidence: read-the-code certain.

### CB-7 — `ss_portfolio.broker.AlpacaBroker._paper` substring check can put live trading into REAL-MONEY mode silently
- File: `packages/portfolio/src/ss_portfolio/broker.py:106`
- What's wrong: `self._paper = 'paper' in base_url.lower()`. Any URL that omits the substring "paper" (e.g. a typo `https://papr-api.alpaca.markets`, a custom proxy, or a future Alpaca rebrand) flips this to `False` → `TradingClient(..., paper=False)`. The in-code comment already flags this risk.
- Why it matters: if the user-controlled `ALPACA_BASE_URL` env var lands without the magic substring, the broker will happily trade real money. The dry-run rail still catches it because dry-run is the default — but `--live` plus a typo'd base URL = real-money submission.
- Suggested fix: explicitly require `ALPACA_PAPER=1` (or equivalent) to opt into paper, and `ALPACA_LIVE=1` to opt out — never infer from the URL.
- Severity: **3** (gated by the dry-run rail; still a footgun).
- Confidence: read-the-code certain.

### CB-8 — `AlpacaBroker.submit_orders` blanket `except Exception` masks transient API/network failures
- File: `packages/portfolio/src/ss_portfolio/broker.py:248-256`
- What's wrong: every exception (per-symbol rejection, 5xx outage, auth refresh, network timeout, `KeyboardInterrupt` via Exception subclassing in some libs) is swallowed and logged as a per-symbol rejection. The TODO comment in the source acknowledges this.
- Why it matters: an Alpaca outage mid-loop will silently zero every remaining order; the `LiveRunResult.rejected_orders` list will fill with one entry per untouched symbol, but the **portfolio state diverges from intent**. The next run will then re-diff against the partially-rebalanced book and may produce surprising orders.
- Suggested fix: classify into `(SymbolReject, RateLimited, ServerError, AuthError, NetworkError)` per `alpaca-py`'s exception hierarchy; re-raise the latter four after at most a couple of retries.
- Severity: **3**.
- Confidence: read-the-code certain.

### CB-9 — `realized_vol`'s NaN-fill before cumsum is harmless but the pattern is fragile
- File: `packages/features/src/ss_features/vol.py:30-41`
- What's wrong: `rets_clean = np.where(np.isnan(rets), 0.0, rets)` replaces only the leading NaN (`rets[0]`) for a single ticker with finite history. But the loop only runs from `i=window`, and at `i=window` the cumsum slice is `cs[window+1] - cs[1]` (excludes `rets[0]`). Correct **only because** there is exactly one leading NaN in `log_returns`. If a future call passes a series with interior NaNs (e.g. half-loaded ticker), they all become silent zeros — biasing volatility down.
- Why it matters: `realized_vol_matrix` iterates per-column. Mid-history NaN gaps (delisting? halted bars?) silently zero, biasing realized vol for that ticker low for ~window bars.
- Suggested fix: assert no interior NaN at the top, or propagate NaN forward through the rolling window.
- Severity: **2**.
- Confidence: read-the-code certain.

## Look-ahead / PIT risks

### LA-1 — Forward-target overlap with `forward_skip > 0` allowed across walk-forward boundaries
- File: `apps/factor/src/factor/train.py:241-243`
- What's wrong: training labels at the last train block extend `i + rebal_days + forward_skip` bars forward. With default `step_window_blocks = val_window_blocks` and `forward_skip > 0`, the **training label** at `train_slc.stop - 1` uses prices that fall inside the val window. This is a label-side overlap, not a feature-side leak — the model's training target peeks into val.
- Why it matters: rank-IC training fit minimizes a loss that uses future return data which is part of val. The val IC is still computed on val-window labels disjoint from train labels (the val_slc starts after the last train rebal_idx), but training "knew" about price moves in the early val window. Could inflate val IC modestly when `forward_skip` is set.
- Suggested fix: extend the train slice's effective end to `train_slc.stop - ceil((forward_skip + rebal_days) / rebal_days)` blocks, or insert a `purge` gap between train and val a la López de Prado purged k-fold.
- Severity: **3** when `forward_skip > 0`; harmless at `forward_skip=0` (current default).
- Confidence: strongly-suspect.

### LA-2 — Stale-data freshness rail uses calendar days, not trading days
- File: `apps/regime/src/regime/live.py:115-117`, `apps/relational/src/relational/live.py:111-113`
- What's wrong: `age_days = (now_naive - last_bar).days` is calendar days. Default `max_data_age_days=3` interprets weekends as data staleness. After a long holiday (Thanksgiving Wed close → Mon morning = 5 calendar days), the rail aborts even though no trading day was skipped.
- Why it matters: silent abort with `aborted_reason` — but the operator's log says "stale data" when nothing is stale. Conversely, the inverse failure mode (a feed silently freezes Tuesday at the Friday close on a 4-day holiday week) escapes detection.
- Suggested fix: count trading bars (`len(prices) - position_of_now`) instead of calendar days; or use NYSE calendar.
- Severity: **2**.
- Confidence: read-the-code certain.

### LA-3 — `last_bar.tz` handling depends on Alpaca returning tz-localized timestamps
- File: `apps/regime/src/regime/live.py:115`, `apps/relational/src/relational/live.py:111`
- What's wrong: `pd.Timestamp.now('UTC').tz_convert(None).normalize() - last_bar`. `last_bar` is naive (broker strips tz at line 156 in `broker.py`). The subtraction is naive-naive — works, but assumes UTC throughout. If the broker ever returns NY-local timestamps (or pandas changes default tz handling), this silently mis-computes age.
- Severity: **1**.
- Confidence: read-the-code certain.

### LA-4 — Optuna-search universe is implicitly survivorship-biased upstream of the trainer
- File: `apps/regime/src/regime/trainer.py` (universe filter via `min_history`)
- What's wrong: `min_history=DEFAULT_PER_WINDOW_MIN_HISTORY=630` bars at the universe-loader level requires a ticker to have *current* enough history to support the largest CWT scale — but only tickers *still listed today* (or until the dataset cutoff) get picked. Delisted-mid-window tickers are dropped before training. The Stooq archive nominally includes delisted tickers; the question is whether `load_stooq_matrix(min_history=…)` preserves them.
- Why it matters: classic survivorship bias. Documented as a known limitation in CLAUDE.md for the Kaggle Nasdaq3347 dataset; less clear for Stooq.
- Suggested fix: verify `load_stooq_matrix`'s behavior on delisted tickers; if it filters them, expose a `keep_delisted=True` knob.
- Severity: depends on loader behavior; potentially **4**.
- Confidence: worth-investigating.

## Underreporting / silent failure paths

### UF-1 — DSR aggregator silently skips arcs missing the expected stream key, with no exit code
- File: `apps/docs/scripts/compute_dsr.py:207-214`
- What's wrong: on missing NPZ or missing `stream_key`, prints `[skip]` and moves on. The leaderboard published from this output then misses the row entirely — and the recent commit `da79b80` (per the git log) deliberately added this skip to guard against stale NPZs. If a *current* run's NPZ schema drifts (e.g. `oos_block_returns` renamed to `block_returns_oos`), the arc disappears from the DSR ranking without any non-zero exit code.
- Why it matters: a half-broken refactor of the dumper produces a quietly-shorter leaderboard. The "skip" message is in stdout; a cron-driven docs build does not surface it as an error.
- Suggested fix: require an explicit allowlist of arcs to skip (`KNOWN_PENDING={...}`); raise on any spec whose NPZ exists but lacks the key.
- Severity: **3**.
- Confidence: read-the-code certain.

### UF-2 — DSR `sharpe_std` defaults to `1/sqrt(n_obs)` (null SE) for every arc, **massively under-deflating**
- File: `packages/portfolio/src/ss_portfolio/deflated.py:209-213`, used at `apps/docs/scripts/compute_dsr.py:227,233`
- What's wrong: `standardize_oos` is called *without* `trial_sharpes` and *without* `sharpe_std` for every arc in `SPECS`. The fallback uses `1.0 / sqrt(n_obs)` — the null standard error of a Sharpe estimate. Bailey & López de Prado's DSR formulation uses the **cross-trial dispersion** of trial Sharpes — typically *much larger* than `1/sqrt(n)`. Under-stating `sharpe_std` shrinks `expected_max_sharpe` → shrinks the deflation → inflates DSR/`deflated_tstat`.
- Why it matters: this is the leaderboard's primary ranking key. Every arc is being scored against a too-easy benchmark. Arcs ranked `confirmed-OOS` may not be once a realistic trial-Sharpe dispersion is used.
- Suggested fix: either persist per-trial Sharpe arrays alongside each NPZ (the right answer) or set a per-arc conservative `sharpe_std` based on typical cross-trial Sharpe dispersion observed in the workspace (~0.3 annualized).
- Severity: **5** — directly biases the published cross-arc ranking.
- Confidence: strongly-suspect (depends on what dispersion the workspace's typical sweep produces; worth measuring once before deciding the fix).

### UF-3 — DSR aggregator pools daily and block streams under a single `periods_per_year` key that defaults to 252
- File: `apps/docs/scripts/compute_dsr.py:199-201`
- What's wrong: `_periods_per_year(d, default=252.0)` — if a returns NPZ omits `periods_per_year`, the aggregator treats its stream as daily. Several arc dumpers (the factor walk-forward, `apps/factor/scripts/.../universe_pivot_walkforward.py` etc.) emit block streams. If any of them omit the key, their annualized Sharpe and DSR will be wrong by `sqrt(rebal_days)` — a factor of ~3-5x on a 5-day rebal stream.
- Why it matters: silent miscomparison of arcs on the leaderboard. A 5-day-block stream falsely annualized as daily would have its annual Sharpe inflated 2-3x and its DSR severely inflated.
- Suggested fix: make `periods_per_year` a required NPZ key; raise (don't default) if missing.
- Severity: **5** if any current arc's dumper omits it; **3** as a forward-looking risk.
- Confidence: read-the-code certain that the fallback exists; **worth-investigating** which arcs actually omit the key (sample a few NPZs).

### UF-4 — `compute_dsr` borrow charge of `0.5 * (bps/yr) / ppy` assumes a specific long-short construction
- File: `apps/docs/scripts/compute_dsr.py:217-219`
- What's wrong: `strat = strat - (bps/1e4) * (1/ppy) * 0.5`. The `0.5` is the gross-short fraction of an L1=1 dollar-neutral book. But `block_port_returns_long_short_np` constructs `w` with `leverage=1.0` over a `l1.maximum(1e-12)` normalized z-score → `sum(|w|) ≈ 1`, so gross short is indeed ~0.5. **However**: the same 0.5 multiplier is applied to `factor-5d-LS-skip1-*` AND `lie-shape-knn-LS-*` AND any future arc whose stream isn't built the same way. The `momentum-12-1` and `low-vol-bab` arcs declare "borrow already charged inside the stream" via the `borrow_bps_yr=0` skip, so they're guarded — but every new arc author must remember this convention.
- Suggested fix: put the borrow inside the per-arc dumper, not the aggregator. Or carry a `gross_short_fraction` field on `ArcSpec` so the constant is explicit.
- Severity: **2** today; **4** as a foot-gun for new arcs.
- Confidence: read-the-code certain.

### UF-5 — Walk-forward harness skips windows that don't fit without surfacing the gap in the result object
- File: `packages/features/src/ss_features/walkforward.py:46-52`
- What's wrong: `block_windows` silently drops the partial tail. `apps/factor/.../train_walkforward.py:357-361` raises only when **zero** windows fit, not when fewer than expected fit. A change in `n_blocks` (e.g. data range shortened by one re-prep) can drop one window without any log message.
- Why it matters: cross-arc DSR ranking compares arcs with assumed-equal `n_obs`. A silent window drop changes `n_obs` and the deflation term.
- Suggested fix: emit a warning when `len(slices) < expected`; require the caller to pass `expected_n_windows` for the DSR-producing path.
- Severity: **2**.
- Confidence: read-the-code certain.

### UF-6 — Many script-level `except Exception` blocks catch and continue per-window failures
- Files: `apps/pairs/scripts/run_walkforward.py:177-181`, `apps/factor/scripts/...` (~20 sites listed in scan), `apps/vol/scripts/...`
- What's wrong: per-window/per-pair failures are caught and recorded as a skip + print. The aggregate stats (mean_val_sharpe, pos_window_fraction) then computed over the **survivors only**, with no record of how many failed.
- Why it matters: a regime where 4/6 windows pass and 2/6 silently throw looks like `mean = mean_of_4` not `mean_of_6_with_2_nan`. The leaderboard row then reads as if all windows ran.
- Suggested fix: at minimum, log the failed-window count next to the verdict; ideally fail the run if any non-deterministic window crashes.
- Severity: **3**.
- Confidence: read-the-code certain.

## DSR ladder correctness (branch-specific)

The recent branch ships a cross-arc Deflated-Sharpe ranking driven by
`packages/portfolio/src/ss_portfolio/deflated.py` and aggregated by
`apps/docs/scripts/compute_dsr.py`. Findings specific to this work:

1. **`sharpe_std` fallback systematically under-deflates** (UF-2 above). This is the single
   most important DSR issue. The fallback `1/sqrt(n_obs)` is the *Sharpe estimator's null SE*, not the cross-trial dispersion the DSR formula needs. Every leaderboard row is using the fallback.
2. **`periods_per_year` per-NPZ default of 252** (UF-3) pools block and daily arcs unsafely. Audit each `*-returns.npz` file in `Output/` to confirm the key is set.
3. **Trial-count reconstruction is by hand** (`SPECS` in `compute_dsr.py:57-196`). The
   provisional counts are sometimes "round up when unsure" — fine, but the conservative-vs-anti-conservative direction depends on whether under-counting or over-counting is the bigger sin. For DSR, **under-counting trials → under-penalizes → inflates DSR**. So the policy is anti-conservative as currently stated.
4. **`compute_dsr` stale-NPZ skip is silent** (UF-1). Recent commit `da79b80` deliberately
   added skip for stale artifact; if a current run's stream key drifts, the arc vanishes.
5. **Borrow charge gross-short factor `0.5` is implicit** (UF-4). Applies to L/S arcs whose
   stream sums to L1≈1; not robust to alternative constructors.
6. **Per-block entry-cost spurious charge** (CB-3) propagates into the DSR stream via
   `block_port_returns_np` — small uniform bias, but it does shift every factor-arc DSR by a constant.
7. **`probabilistic_sharpe` denominator guard** (`deflated.py:117-119`) returns NaN when
   `denom <= 0`. This silently nan-outs PSR/DSR for fat-tailed-positive-skew streams
   (which the leaderboard *would* want to rank highly). Looks like missing data instead
   of a degenerate denominator.
8. **Acklam ppf** (lines 48-77): accuracy ~1.15e-9 — fine for the formula's needs. No bug.

Net: the DSR pipeline computes a sensible relative ranking *given a fixed (and
underestimated) `sharpe_std`* but the absolute DSR values are not interpretable as
"P(skill, not luck-of-T-coin-flips)" because the dispersion input is wrong.

Confidence: read-the-code certain on the mechanics; strongly-suspect on the magnitude of impact (depends on cross-trial Sharpe dispersion in current arcs, which would need a measurement).

## Cross-cutting inconsistencies

1. **Two `block_sharpe` implementations.** `ss_portfolio.sharpe.block_sharpe_with_costs`
   (numpy) and `factor.objectives.block_sharpe` (tinygrad). The math agrees but they live
   in two places. A change to one (e.g. fix CB-3) needs mirroring in both. Recommend:
   factor the cost arithmetic into a numpy primitive that both call.

2. **Cost models vary by arc.**
   - `apps/factor`: `commission_bps=10`, applied via `0.5 * L1(delta_w)` (long-only) or
     `L1(delta_w)` (long-short). Half-factor logic documented but easy to mis-apply.
   - `apps/pairs`: `commission_bps=10` × 2 "per leg-flip" (entry + exit).
   - `apps/dca`: `commission_bps=10` via `cfr.baselines.PassiveEW`. Need to verify same cost convention.
   - `apps/gate`: no commission on gate transitions; explicitly omitted.
   - `apps/vol`: cost charged via short-vol PnL accounting (`ss_iv.short_vol`).
   - `compute_dsr` borrow charge: only on certain L/S arcs, with the 0.5 gross-short
     convention baked in (UF-4).

   Cross-arc DSR ranking compares arcs whose cost conventions differ — **the ladder
   is not apples-to-apples on cost**. The `findings/cross-arc-deflated-sharpe-ranking.md`
   page should document the convention map per arc.

3. **Timestamp handling.** Broker emits tz-naive timestamps (`broker.py:156`). `live.py`
   strips tz from `now()`. Pairs uses `pd.DatetimeIndex` directly. Gate uses
   `np.datetime64`. No consistent pattern; mostly works because everything is naive UTC
   or naive local. One future timezone-aware Alpaca change would ripple.

4. **`periods_per_year` convention.** DSR aggregator falls back to 252. Each arc dumper
   *should* write the key explicitly. No central declaration that this is required.

5. **NaN handling at boundaries.** Some kernels return NaN warmup (RSI strided, CCI),
   some return neutral values (RSI matrix: 50.0), some `nan_to_num` to 0 (`factor.train`).
   Inconsistent — a downstream consumer that's robust to NaN may silently see zeros from
   `factor.train` and not flag a warmup region.

6. **Universe definition.** Each app maintains its own universe filter logic; survivorship-
   bias prevention is documented per-app but not centralized in `ss_loaders`.

7. **`commission_bps` units.** Some places `commission_bps=10.0` means 10 bps total turnover-
   weighted; some (pairs) means 10 bps **per leg**; some (broker) means nothing because real
   Alpaca is $0. The `commission_bps` arg name should be qualified as `commission_bps_per_leg`
   or `commission_bps_per_turnover` everywhere.

## Executive summary

1. **UF-2 (sev 5)**: every leaderboard row's DSR uses `sharpe_std = 1/sqrt(n_obs)` as a
   fallback because no arc passes `trial_sharpes` or an explicit `sharpe_std` to
   `standardize_oos`. This is **the null SE of a single Sharpe**, not the **cross-trial
   dispersion** the DSR formula requires. Result: deflation term is too small → DSR/`deflated_tstat` inflated. The cross-arc ranking is internally consistent but the absolute DSR values are not interpretable as published.
2. **UF-3 (sev 5 contingent)**: `compute_dsr` falls back to `periods_per_year=252` when an
   NPZ omits the key. Any block-return arc that forgets the key has its annual Sharpe inflated by `sqrt(rebal_days)`. Quick audit of the existing `Output/*-returns.npz` files would tell us if this fires today.
3. **CB-1 (sev 3)**: pairs walk-forward aggregator divides each pair's `.fillna(0)` series by
   total pair count, under-weighting pairs that are active on partial days. The pairs
   leaderboard row understates the actual 1/N-on-active book.
4. **CB-4 (sev 3 live)**: `apply_position_cap` silently inflates total weight mass to 1.0 in
   the degenerate uniform-distribute path. Risk-rail surprise for live strategies that
   intentionally hold cash.
5. **CB-5 + CB-6 (sev 2 each, latent)**: `gate.aggregate.breadth` uses all-time max universe size; `ss_wavelets.precompute_windows` uses all-time per-ticker power mean. Both are documented soft-look-aheads. Neither is a return leak today; both are pipeline land mines if/when a new caller plugs in a non-scale-invariant divergence or a longer panel.
6. **UF-1 + UF-6**: many silent skip-and-continue paths (DSR stale-NPZ, pairs/factor `except Exception` in walk-forward loops). Leaderboard rows are produced as if all windows ran, even when some failed. Aggregate stats compute over survivors.
7. **CB-3 (sev 2 systematic)**: `block_sharpe` charges full one-sided initial cost on every walk-forward val slice. Affects every factor arc's published val Sharpe and the DSR streams that consume `block_port_returns_np`. Uniform bias; small but constant.
8. **Cost conventions are not unified across arcs** — DSR ranking is comparing apples to slightly-different oranges on cost. The borrow-charge fix in the aggregator (`0.5 * bps/yr`) papers over only one source.
9. **CB-7 (sev 3 live)**: broker `_paper` substring check on URL is brittle; a typo'd `ALPACA_BASE_URL` puts the client into real-money mode. Dry-run default mitigates but `--live` + typo = real-money trade.

Recommended immediate actions: (a) measure cross-trial Sharpe dispersion across the
existing factor walk-forward sweeps and back-fill `sharpe_std` in `compute_dsr`;
(b) require `periods_per_year` as a non-default NPZ key; (c) fix `apply_position_cap`'s
degenerate path to preserve input mass; (d) fix pairs aggregator's partial-day divisor.
The other findings can wait for the next refactor pass.
