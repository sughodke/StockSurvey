## TL;DR

**Recommendation: `apps/factor` walk-forward, `loss_kind='studentized_sharpe_diff_vs_ew'`,
linear head, 5d rebal, factor-narrow universe, with the universe-EW per-block
stream as the benchmark `port_b`.** This is the only candidate that combines
(a) n_obs large enough that the delta-method s.e. is not dominated by null
estimation noise, (b) a parameter (head weights + log-temperature) that flows
end-to-end into per-block portfolio returns, (c) a tinygrad trainer that
*already* constructs the `(weights → block_port_ret)` pipeline the loss needs,
and (d) a directly-comparable existing baseline (the `block_ir_vs_ew` arm)
that gives a known-IR ceiling to measure lift against.

**MVP:** add `'studentized_sharpe_diff_vs_ew'` to the `loss_kind` enum in
`apps/factor/src/factor/train_walkforward.py`, wire `block_studentized_sharpe_diff`
against an in-loop EW per-block return stream computed from `blr_train` +
`mask_train`, run the standard 5d-LO walk-forward harness on factor-narrow,
report mean-val ΔSR/s.e. + bootstrap CI per window. ~80 LOC, ~1 day of work,
pre-registered.

## The MVP plan for #1 — Factor 5d LO + studentized-SR-diff-vs-EW loss

### Why factor-app, why this loss, why now

- **The pipeline is already there.** `train_scorer_walkforward` produces
  per-block portfolio return Tensors inside the training loop (via the
  softmax → cost → reduce machinery in `block_sharpe`). All we need is to
  (a) stop at the *stream* (mirror `block_port_returns_np`'s logic in
  Tensor land, not numpy), (b) construct an EW per-block stream Tensor
  from `blr_train * mask_train` over the same rebal grid, (c) feed both
  to `block_studentized_sharpe_diff`. The EW stream needs no learned
  parameters and no costs (it's the frictionless benchmark — same
  convention as `block_ir_vs_ew`).
- **n=936 blocks** at 5d rebal × 9 walk-forward windows is *the* point in
  the workspace where the delta-method s.e. has bite. At n≤50 (vol-v3,
  DCA+vol overlap) the parametric s.e. variance dominates the SR-diff
  numerator, and the gradient signal is shot noise. At n=936 a
  studentized-SR-diff t-stat of 1.0 corresponds to ~0.07 SR units of
  separation — comfortably above the per-window granularity of the
  existing leaderboard.
- **The baseline is the `ir_vs_ew` arm.** The IR loss already trains for
  *active* return per unit tracking-error vs EW. The studentized-SR-diff
  loss trains for the *t-stat of the SR difference* — different shape:
  IR loss is location-free in the s.e., while studentized-SR-diff loss
  *down-weights* moves that increase return variance. Expected
  difference: cleaner risk-adjusted alpha, smaller leverage drift, easier
  bootstrap-CI clearance. We have a direct comparison row to drop next
  to `ir_vs_ew` on the leaderboard.

### Concrete change list

1. **`apps/factor/src/factor/objectives.py`** — add a Tensor mirror of
   `block_port_returns_np` (so the per-block stream is differentiable end
   to end). Name it `block_port_returns_softmax_lo` (or similar). It
   already exists implicitly inside `block_sharpe`; refactor that fn to
   compose two steps (`port_block_ret` builder + reduce) so the builder
   can be reused. **~30 LOC** (refactor + new helper).
2. **Add `block_ew_returns` helper (Tensor)** that takes `(blr_rb, mask_rb)`
   and returns the per-block frictionless EW return stream. **~10 LOC.**
3. **`train_walkforward.py`** — add `'studentized_sharpe_diff_vs_ew'` to
   `valid_losses`; wire the training-step branch:
   ```python
   elif loss_kind == 'studentized_sharpe_diff_vs_ew':
       port_a = block_port_returns_softmax_lo(
           out, log_temperature, blr_train, mask_train, commission_frac)
       port_b = block_ew_returns(blr_train, mask_train)
       loss = -block_studentized_sharpe_diff(port_a, port_b)
   ```
   `train_temp = True` for this arm (loss is *not* scale-invariant — the
   softmax temperature changes both SR_a and its s.e.). **~20 LOC.**
4. **Driver script** under `apps/factor/scripts/modal/` (clone the
   existing 5d-LO walk-forward Modal entrypoint; just flip the `loss_kind`
   flag). **~20 LOC.**
5. **Eval reporting** — at the result level, additionally compute and
   record (a) per-window bootstrap-CI Sharpe-diff vs EW using
   `ss_portfolio.sharpe_difference_ci` on `val_block_returns` against the
   in-window val-EW stream, (b) the parametric CI from the same call to
   `parametric_ci` as a sanity check vs bootstrap. Land both as columns in
   the leaderboard row.

**Total: ~80 LOC, ~1 day of work including a smoke test.**

### Pre-registration (lock before running)

- **Universe:** `factor-narrow` (existing tag).
- **Windowing:** 5d rebal, train_window_blocks=63, val_window_blocks=39,
  step=val (existing tag `factor-walkforward-5d`).
- **Arm A (test):** linear head, `loss_kind='studentized_sharpe_diff_vs_ew'`,
  `train_temp=True`, all else default.
- **Arm B (baseline):** linear head, `loss_kind='ir_vs_ew'`, same hyperparams.
- **Decision metric:** mean across windows of bootstrap-CI
  (Ledoit-Wolf 2008, 95%, B=10000) of `(val_block_returns_A −
  val_ew_block_returns)` minus the same for arm B. **Decision: arm A wins
  if (i) mean-window ΔSR/s.e. > arm B by ≥0.15 t-units, AND (ii) at
  least 5/9 windows have arm-A bootstrap CI strictly above arm B's bootstrap CI
  point estimate.**
- **Falsification bar:** if arm A's mean-window bootstrap CI on (val − EW)
  does not exclude zero at 95% on the *aggregated* OOS stream
  (`oos_block_returns` concat across 9 windows), record verdict
  `confirmed-null` against the DCA-canonical bar regardless of relative
  performance vs arm B.
- **Sharpe column:** mandatory per `CLAUDE.md`. Report mean val Sharpe
  long-only + mean val IR-vs-EW + mean val ΔSR/s.e. with parametric s.e.

### What would make us *not* run this

- If the refactor in step 1 reveals that `block_sharpe`'s per-block
  reduction is load-bearing for numerical stability in tinygrad (the
  `port_block_ret.std() + 1e-9` floor catches degenerate-variance bars),
  we'd need to add the same floor inside `block_studentized_sharpe_diff`.
  The fn already has an `eps` floor; should be fine.

## Anti-recommendations (don't try these first)

- **Vol-v3 gate threshold (candidate #7).** Looks appealing because the
  rule "fire only when VIX > 126d-median" is the most binary-looking knob
  in the deployment stack, and replacing the hard step with a soft sigmoid
  is the textbook differentiability move. *Don't.* The arc closed with
  `partial-OOS` at n=33 fired-rebals. Training a scalar threshold over
  33 obs converges to either fire-always (kills the gate's point) or
  fire-never (degenerate). The parametric s.e. at n=33 with SR≈1 has
  half-width ~0.6 t-units — wider than the entire leaderboard's
  inter-arc spread. **Wait for more data or paid options data.**
- **DCA + vol ensemble vega-scale (candidate #8).** Tempting because the
  ensemble is the candidate deployment and the methodology rewrite
  explicitly called this out as "plausibly positive but not significant."
  But: n=29 overlap blocks, *one* scalar parameter, and the
  methodology-rewrite finding already establishes that under Ledoit-Wolf
  bootstrap CI no value of `vega_scale` clears the 95% bar on the current
  data. Training directly against `studentized_sharpe_diff_vs_dca` will
  produce a "best" `vega_scale` that overfits the 29 obs and almost
  certainly fails on the same falsification bar that grid search failed.
  *The data is the binding constraint, not the search procedure.*
- **Gate predictor as linear layer (candidate #5).** The wrong-bar
  problem: `apps/gate` already doesn't clear DCA today. Training its
  parameters directly against ΔSR vs DCA changes nothing if the
  feature set lacks the signal — it just concentrates the search at
  the local-optimum corner of an empty space.
- **Regime trainer port (candidate #9).** Optuna over CWT-power-divergence
  weight-function choice has categorical hyperparameters (KL vs JS vs
  cosine vs L2). Gradient over a categorical is meaningless. Would
  require wholesale rewrite of `weights_regime` as a learnable composition
  — large engineering cost for unclear lift on an arc that already
  closed with `confirmed-null` against DCA in the methodology rewrite.

## The honest caveat

The methodology rewrite established that under Ledoit-Wolf bootstrap CI
**no arc currently beats DCA at 95%**. The new loss does not escape this
— it *concentrates* the data-snooping risk into the training objective.
The studentized-SR-diff loss is the asymptotic limit of the same
bootstrap CI used as the falsification bar (Lo 2002), so a perfectly-fit
training-time t-stat predicts the OOS bootstrap-CI t-stat only up to
generalization gap + sampling variance.

**What this changes:** the candidate #1 plan above pre-registers the
falsification bar (mean-window bootstrap CI excludes zero on aggregated
OOS) *and* requires arm A to beat arm B (the existing `ir_vs_ew`
training arm) by ≥0.15 t-units. Either of these can fail:

- Arm A could clear arm B but still fail the bootstrap CI bar → record
  `confirmed-null` against DCA-canonical, but `partial-OOS` for "this
  loss is a strictly better training objective than IR for the same
  outcome quality." Useful methodology finding, no shippable strategy.
- Arm A could fail to clear arm B → record `confirmed-null` for the
  loss itself; the rank-IC / IR baselines remain canonical.
- Arm A could clear both bars → first beat-DCA result in the rewrite,
  worth deployment work and an arc summary.

The point of running #1 first is that it's the only candidate where the
falsification bar is well-defined *and* clearable in principle. The
others either fail on data-shape (vol-v3, DCA+vol ensemble), wrong-bar
(gate), or differentiability (regime, relational). Run #1, expect a
`partial-OOS` methodology result, treat any beat-DCA outcome as a
genuine surprise.
