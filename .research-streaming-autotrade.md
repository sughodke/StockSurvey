# Streaming / Event-Driven Stock Autotrading — Architecture & Corporate-Actions Brief

*Compiled 2026-05-22 for StockSurvey. Scope: how to move from batch walk-forward over Stooq daily archives toward a point-in-time-correct event stream that backtest and live execution can share.*

---

## TL;DR

1. **The shared abstraction every serious framework converges on is an event queue with typed events** — `MARKET`, `SPLIT`, `DIVIDEND`, `SYMBOL_CHANGED`, `DELISTING`, `SIGNAL`, `ORDER`, `FILL`. Zipline, QSTrader, NautilusTrader, and LEAN all look like the Halls-Moore design at a high level; what differs is rigor around determinism, time semantics, and corporate-action timing.
2. **Adjusted close is a research lie.** It is convenient for charting but destroys signal/execution parity. Every production system the literature respects (LEAN, Zipline, Norgate, CRSP-based research) stores **unadjusted prices + a separate corporate-actions ledger**, and applies adjustments **as-of the simulation clock**. Stooq's "already-adjusted" archive is fine for prototyping but is the wrong shape for a streaming engine.
3. **Use a permanent security ID, never the ticker.** CRSP's `PERMNO` is the gold standard; Bloomberg/OpenFIGI's `composite FIGI` is the open analog. FB→META, GOOG/GOOGL share classes, and ticker reuse (the same string assigned to a different company years later) all silently corrupt joins keyed on ticker. LEAN's `Symbol` object is its solution; replicate that shape.
4. **Point-in-time universe membership is its own event stream.** Index additions/deletions, IPO listing dates, delistings, and free-float reconstitutions must arrive as events with the same clock as price bars — otherwise "rebal-on-S&P-500" is wildly look-ahead-biased. Norgate's historical constituents and CRSP's names file are the canonical sources; free data does not solve this.
5. **Backtest/live parity is the architectural design goal**, not a nice-to-have. NautilusTrader's pitch is the cleanest articulation: same event types, same message bus, same execution semantics; the only thing swapped at the boundary is the data adapter and the broker adapter. QSTrader and LEAN make the same claim. Adopt this pattern explicitly.
6. **Free corporate-actions tapes are uneven.** Polygon (free tier is rate-limited but the *data* is complete), Tiingo, and EODHD all carry splits + cash dividends. Yahoo has documented inconsistencies — pre-split dividends sometimes not re-scaled when OHLC is. Alpha Vantage is fine for prototyping, weaker for delisted history. SEC EDGAR 8-Ks contain the *announcements* but you have to parse them; do not use as a primary feed.
7. **Dollar/volume/imbalance/CUSUM bars (López de Prado) are an orthogonal concern.** They restructure *sampling* of the price stream, not the corporate-actions firehose. They matter if you care about i.i.d.-ish features for ML labelling; they don't fix split timing or ticker reuse. Build the corporate-actions plumbing first.
8. **The "adjustment boundary" is the single hardest bug.** When a split occurs in live trading, your *indicator state* contains pre-split bars; the next bar arrives post-split. Either you replay history through the new adjustment factor (expensive) or you store unadjusted internally and apply adjustment at read-time (correct). QuantConnect's docs explicitly warn that signals will diverge from backtest if you don't.
9. **Ex-date is the bar that matters** for cash dividends in a price-stream sense (that's when the close drops by ~the dividend); record-date is for who-gets-paid; pay-date is for cash bookkeeping. Three different timestamps, three different ledger updates. Most retail frameworks conflate them.
10. **For a pure Python implementation you can ship in a weekend**: copy the QSTrader/Halls-Moore queue skeleton, but add a `CorporateActionEvent` type emitted *before* the bar of its ex-date and consumed by an `AdjustmentService` that mutates the portfolio (split → multiply positions, dividend → credit cash) *before* the strategy sees the new bar. Anything else gets the ordering wrong.

## Reference frameworks — stream + corporate-actions models

### Zipline (Quantopian → ml4trading.io Reloaded)

- **Stream model.** Daily/minute bars iterated via a `DataPortal` that wraps a `BcolzDailyBarReader` (prices) and an `SQLiteAdjustmentReader` (corporate actions). Strategies subscribe via Pipeline (vectorized factor evaluation) or the `handle_data` callback (event-loop-ish).
- **Corporate-actions API.** `SQLiteAdjustmentWriter` writes four tables: `splits`, `mergers`, `dividends`, `stock_dividends`. Splits/mergers carry `(sid, effective_date, ratio)`. Dividends carry the full `(declared_date, ex_date, record_date, pay_date, amount)` tuple. Stock dividends carry `(payment_sid, ratio)`. Pipeline applies adjustments *as-of* the simulation clock — historical windows are re-scaled on-the-fly.
- **Gotchas.** Bundle ingestion is the choke point: you must supply unadjusted OHLCV + a separate dividends/splits dataframe. Bad/missing adjustments silently distort backtests. The Reloaded fork (Stefan Jansen) is the maintained version; the original Quantopian repo is frozen.
- **API shape (illustrative):**
  ```python
  writer = SQLiteAdjustmentWriter(conn, equity_daily_bar_reader, calendar)
  writer.write(
      splits=splits_df,          # sid, effective_date, ratio
      mergers=mergers_df,        # sid, effective_date, ratio
      dividends=dividends_df,    # sid, ex_date, declared_date, pay_date, record_date, amount
      stock_dividends=stock_div_df,  # sid, ex_date, payment_sid, ratio
  )
  ```

### QuantConnect LEAN

- **Stream model.** Event-driven slice loop; `OnData(Slice)` receives a fused snapshot per bar. Symbols are first-class objects (`Symbol` class) that are *stable across ticker changes*. Built-in `SymbolChangedEvent`, `Split`, `Dividend`, `Delisting`, `SymbolChangedEvents` are all delivered to `OnData`.
- **Corporate-actions API.** `DataNormalizationMode` ∈ `{Raw, Adjusted, SplitAdjusted, TotalReturn}` chosen at subscription time. In `Raw` mode you get the un-adjusted tape plus discrete corporate-action events. In `Adjusted` mode prices are pre-adjusted but events still fire. **LEAN's docs explicitly warn**: backtest in `Adjusted` and live in `Raw` and your indicator state diverges at the next corporate action.
- **Gotchas.** Subscription-mode mismatch between backtest and live is the canonical bug. `Symbol` ↔ ticker mapping requires `SecurityIdentifier`; never key strategy state on the ticker string.

### NautilusTrader

- **Stream model.** Rust-native engine; a single deterministic `MessageBus` handles all events at nanosecond resolution. Same engine binary runs backtest and live — only the data adapter and execution adapter swap. Marketed as "research-to-live parity, no code changes."
- **Corporate-actions API.** Not its primary focus (built for FX/crypto/HFT first); equity corporate-action handling is less mature than LEAN. Custom event types are first-class, so you'd subscribe a `CorporateActionsAdapter` that emits typed events.
- **Why it's worth studying.** The architectural discipline — typed events, deterministic clock, message bus — is the cleanest existing template for what you're building. Treat as reference architecture, not necessarily as the runtime.

### QSTrader (Halls-Moore / QuantStart)

- **Stream model.** Canonical pedagogical event-driven backtester: a `collections.deque` event queue, `MarketEvent → SignalEvent → OrderEvent → FillEvent`. `DataHandler` produces market events; `Strategy` consumes them; `Portfolio` consumes signals; `ExecutionHandler` consumes orders. Same components plumb to live.
- **Corporate-actions API.** **Effectively absent.** You're expected to pre-adjust your CSV. This is the gap you'd fill in your implementation.
- **Why it's the right starting skeleton.** ~500 lines, fully readable, the abstraction is correct. Add `CorporateActionEvent` and an `AdjustmentService` and you have what you want.

### backtrader

- **Stream model.** `cerebro` runs a multi-asset event loop; `next()` callback per bar. Pre-runs all lines (indicators) before user `next()`, which is a vectorized shortcut, not a pure stream.
- **Corporate-actions API.** Only via `adjclose=True` on the data feed (consume pre-adjusted prices) or a custom `Dividends` indicator that adds cash to broker on payment date. Community-acknowledged weakness; users who care write custom feeds.
- **Verdict.** Workable for single-asset / pre-adjusted prototypes. Not where to look for streaming corporate-actions design.

### vectorbt / vectorbt PRO

- **Stream model.** **Not actually event-driven.** Vectorized signal-array → portfolio simulation. The "PRO" version adds a callback-based per-bar simulator but it's still array-shaped under the hood.
- **Corporate-actions API.** None. Inputs are pre-adjusted price arrays. This is fine for your existing batch walk-forward; it's not what you'd build the stream on.

### Backtesting.py / `bt`

- Both pre-adjusted-prices-in, returns-out. No corporate-actions modeling. Skip for this purpose.

## The hard problems (and how to handle them)

1. **The split-adjustment boundary between historical and live.** When the live stream emits a post-split bar, all in-memory indicator state (RSI, CWT power, moving averages) was computed on pre-split prices. *Solution:* store internal state in **unadjusted-price space**, apply adjustment factors *only at read-time* when the strategy actually consumes a window. Equivalent: when a `SPLIT` event arrives, fan it out to every indicator's history buffer and re-scale in place. QuantConnect chose the former; Zipline does something close to the former for Pipeline windows.

2. **Ticker reuse and class shares.** FB→META is the easy case (same instrument, new ticker — `SYMBOL_CHANGED` event). The hard cases are (a) post-bankruptcy ticker recycling — `ENRN` got reassigned years later to an unrelated entity; (b) GOOG vs GOOGL (two different instruments, same underlying company, different voting rights, different price series); (c) Class A vs Class B splits announcing a *new* security. *Solution:* key everything by FIGI/PERMNO/internal stable ID; the ticker is a render-time label. Maintain a `(stable_id, ticker, valid_from, valid_to)` history table.

3. **Special-dividend / spin-off timing.** A spin-off creates a new security on the ex-date; the parent's price drops by the spinco's market value. *Solution:* emit a `SPINOFF` event carrying `(parent_sid, child_sid, ratio, ex_date)`; portfolio handler allocates child shares to current parent holders and decrements parent cost basis. Most retail frameworks botch this — Zipline handles it via the `stock_dividends` table; LEAN handles it via the symbol-changed + new-listing events.

4. **What timestamp does a cash dividend occupy in the stream?** Three options, three different ledger effects:
   - **Ex-date bar** → emit `DIVIDEND` event *before* this bar is delivered to strategy. The bar's open/close already reflects the price drop, so this is when the *signal* changes. Backtests should book the receivable on this bar to keep equity curves continuous.
   - **Record-date** → bookkeeping only; not needed in the stream unless you're modelling intra-month T+settlement.
   - **Pay-date** → emit a `CASH_CREDIT` event; this is when buying power actually changes for a live system. *Solution:* emit two events (ex + pay); most strategies only consume ex.

5. **ETF reconstitutions and index inclusion as a streaming event.** When MSFT is added to SPY's basket (or a new S&P 500 inclusion is announced), the price has a measurable "index effect" run-up. *Solution:* a `UNIVERSE_MEMBERSHIP_CHANGED(sid, index, action, effective_date)` event. Most free data does not give you this — it's the principal value Norgate sells. SEC 8-Ks from the index publisher carry the announcements but require parsing.

6. **Delistings with zero recovery vs. delistings via merger.** A merger-delist pays cash; a bankruptcy delist pays nothing. CRSP's delisting return field encodes this. *Solution:* `DELISTING(sid, effective_date, recovery_price)` event; portfolio handler liquidates at the recovery price. Without this you either (a) drop the position silently (survivorship in disguise) or (b) zero it (overstates losses for merger-delists).

7. **Bar timestamp semantics.** Stooq is end-of-day-close-stamped (US TZ). A live IBKR/Alpaca feed may emit start-of-bar-stamped minutes. Mixing the two without an explicit `bar_close_ts` field invites half-bar look-ahead. *Solution:* every event carries both `event_ts` (when it happened in market time) and `available_ts` (when a live system could have known about it). For corporate actions, `available_ts = announcement_ts`, `event_ts = ex_date`.

8. **Dollar/volume/CUSUM bars in a corporate-actions world.** López de Prado's event bars are computed *post-adjustment*: you need an unbroken volume series before you can integrate to a dollar-bar boundary. A 2:1 split halves volume in unadjusted space. *Solution:* compute event-bars against split-adjusted volume + dollar-adjusted price, exactly the dual of price-adjustment.

## Recommended architecture for a Python streaming engine

A pragmatic, ~1k-LOC design that lets `apps/regime` and `apps/relational` `live` reuse the same loop a backtest does. Numpy + asyncio; no heavy frameworks.

```
ss_stream/
├── events.py            # @dataclass(frozen=True) Event hierarchy
├── clock.py             # SimulationClock vs WallClock — same interface
├── universe.py          # PIT universe membership iterator (Stooq listing dates + delisting tape)
├── adjustments.py       # AdjustmentService: split factors, dividend amounts, spinoff ratios
├── sources/
│   ├── stooq_source.py     # unadjusted OHLCV iterator (you'd need to derive from current adjusted-Stooq via the corporate-actions tape — invert the adjustment)
│   ├── eodhd_source.py     # corporate-actions event tape
│   ├── openfigi_source.py  # ticker↔figi mapping cache
│   ├── alpaca_source.py    # live bar stream
│   └── alpaca_actions.py   # live corporate-actions stream
├── bus.py               # asyncio.Queue + typed dispatch
├── portfolio.py         # consumes SplitEvent/DividendEvent BEFORE strategy sees next bar
├── strategy_adapter.py  # wraps existing regime/relational inference into a stream consumer
└── runner.py            # the loop: while events: dispatch; tick clock; emit next bar
```

### Event types

```python
@dataclass(frozen=True)
class Event:
    event_ts: pd.Timestamp        # when it happened in market time
    available_ts: pd.Timestamp    # when a live system would have known

@dataclass(frozen=True)
class BarEvent(Event):
    sid: int                       # stable id, never ticker
    open: float; high: float; low: float; close: float; volume: float
    # all in UNADJUSTED space

@dataclass(frozen=True)
class SplitEvent(Event):
    sid: int; ratio: float          # 2:1 forward split → 2.0

@dataclass(frozen=True)
class DividendEvent(Event):
    sid: int; amount: float
    ex_date: pd.Timestamp; pay_date: pd.Timestamp

@dataclass(frozen=True)
class SymbolChangedEvent(Event):
    sid: int; old_ticker: str; new_ticker: str

@dataclass(frozen=True)
class DelistingEvent(Event):
    sid: int; recovery_price: float | None

@dataclass(frozen=True)
class UniverseMembershipEvent(Event):
    sid: int; index: str; action: Literal["add", "remove"]
```

### Ordering rule (the load-bearing invariant)

For any trading day D, events are dispatched in this order **before** the strategy callback for day D fires:

1. `DelistingEvent`s with `event_ts <= D` → portfolio liquidates at recovery price, position removed.
2. `SplitEvent`s with `event_ts == D` (ex-date) → portfolio multiplies shares; `AdjustmentService` notifies indicator buffers.
3. `DividendEvent`s with `event_ts == D` (ex-date) → portfolio books dividend receivable.
4. `SymbolChangedEvent`s with `event_ts <= D` → ticker renamed in the render layer; SID is unchanged.
5. `UniverseMembershipEvent`s with `event_ts <= D` → universe iterator updates.
6. `BarEvent`s for day D in unadjusted space → adjusted on read by `AdjustmentService.read_window(sid, end=D, lookback=N)`.
7. Strategy callback receives the adjusted window, emits weights/orders.
8. Pay-date `DividendEvent`s → `CashCreditEvent` settles in the broker.

This ordering is the difference between a correct system and a subtly-biased one. Steps 1–5 are missing from most retail frameworks; step 6's lazy adjustment is what gives you backtest/live parity.

### Backtest/live swap

Only two adapters change between modes:

- `sources/` — `StooqSource + EODHDActionsSource` in backtest; `AlpacaBarStream + AlpacaActionsStream` in live.
- `runner.py` — `SimulationClock` advances to next event in backtest; `WallClock` blocks on `asyncio.sleep` in live.

Everything else — strategy code, portfolio bookkeeping, adjustment math — is byte-identical. This is the LEAN/NautilusTrader pitch translated to a ~1k-LOC Python codebase you can actually own.

### Migration path from current StockSurvey

1. **Phase 0 (this week).** Write `events.py` and `bus.py`; have `ss_stream.universe.PITUniverse` consume Stooq's existing delisting metadata and emit `DelistingEvent`s. This unlocks survivorship-free backtests without touching corporate-actions yet.
2. **Phase 1.** Backfill an EODHD/Polygon corporate-actions tape into a local SQLite (Zipline-shape: `splits`, `dividends`, `mergers`, `symbol_changes`). Build an `AdjustmentService` that, given Stooq's already-adjusted close, *inverts* to recover unadjusted prices for storage. (Equivalent: store adjusted-as-of-today and re-scale forward.)
3. **Phase 2.** Wrap existing `regime.inference.target_weights` and `relational.inference.target_weights` in a `strategy_adapter` that consumes `BarEvent`s.
4. **Phase 3.** Replace `regime.live.py` and `relational.live.py` bar-fetch loops with the streaming runner; the four risk rails stay where they are (in `portfolio.py`).
5. **Phase 4.** Optional: layer López de Prado dollar/CUSUM bars as a *resampling consumer* on top of the `BarEvent` stream — they slot in as a derived event type, not a replacement.
