# Audit — decision thresholds across the StockSurvey monorepo

## 1. TL;DR

I found **27 distinct numeric thresholds** in active use across the repo, the
majority of which are nominally trying to answer the same question — "is this
backtest deployable?" — but disagree by factors of 1.5x to 5x. The single worst
contradiction is the deployment-alpha threshold: **the same question is
adjudicated against +0.10 in three CFR scripts, +0.15 in `cfr-phase4.md`,
+0.20 in `pairs/scripts/run_walkforward.py`, +0.30 in `vol/scripts/run_walkforward.py`,
and +0.50 in `factor/scripts/loss_pivot_eval.py`** — none with a stated derivation,
none bootstrap-validated, all applied as binary go/no-go on n=5-6 walk-forward
samples. The PASS/MARGINAL/FAIL tiering layered on top is theater: every
finding I checked produced either a band-edge call that flipped the verdict
on second look (`vol-surface-v0`, `pairs-classical-v0`) or a denominator
artifact (`cfr-macro-gate-final`). My one-sentence recommendation: **scrap the
single-Sharpe verdict apparatus, replace it with a per-strategy-class metric
mapping with bootstrap-confidence intervals on every claim and an explicit
PASS-by-class definition — and stop treating Sharpe as a universal currency
when half the strategies in this repo are tail-behavior or magnitude-aware.**

| value | where defined | what it produces |

| **1 window** | Relational `phase-2 split` (single train/val split) | Used for the entire "Phase-2 wins are mega-cap-specific" arc. n=1 single split, no walk-forward — and the leaderboard itself flags this as "weaker evidence" (reading note 3) — yet `findings/relational-universe-shift.md` was promoted to an operational rule. |

The **n=6 walk-forward is too small to bootstrap "4/6 positive" into a
meaningful test of "does this work in 67% of regimes"**. With n=6, getting
4 positive by chance alone (50% per-window) has p ~ 0.34 under the binomial
null — i.e. **the "4/6 PASS" criterion has a 1-in-3 false-positive rate
against pure noise** before any multiple-comparisons adjustment. The
positive-windows criterion is doing essentially zero filtering. None of the
findings I read computed this.

## 3. Contradictions and double-counting

### 3a. The "paper-trade threshold" exists at +0.10 AND +0.15 simultaneously

`findings/cfr-vs-dca-realistic.md:32`:
> *"...the alpha was below the +0.15 paper-trade threshold from
> [passive-EW benchmark]..."*

`findings/cfr-macro-gate-final.md:41`:
> *"...recovered enough alpha to clear the +0.10 paper-trade threshold."*

`findings/cfr-sensitivity-followup.md:107,110`:
> *"...never clears the +0.10 PASS threshold. The audit's framing... the
> relevant threshold is +0.10 (from `passive-ew-benchmark`), not..."*

But `passive-ew-benchmark.md:90` actually says "+0.15 alpha" as the *pre-test
expectation*, not a registered threshold — both citations attributing a
"paper-trade threshold" to that source are misattributing what's in the source
document. This is a textbook example of a threshold getting laundered into
canonicity by being repeatedly cited.

### 3b. CFR Phase 4d's two thresholds say opposite things about the same row

From `findings/cfr-phase4.md`:
- Line 24: `CFR vs naive uniform +0.101 (>= +0.10 threshold)` -> **PASS**
- Line 35: `mean alpha vs EW +0.056 ... positive but below the +0.15
  paper-trade threshold` -> **partial-OOS on operational floor**

So the same eval — same numbers, same windows — is **simultaneously PASS
(by the in-script +0.10 cut against naive uniform) and partial-OOS (by the
+0.15 narrative cut against passive EW)**. The doc handles this by stacking
the two verdicts, but operationally it means *the question "did Phase 4d
pass?" has no answer*; it depends on which baseline you anchored to.

### 3c. Phase 2 -> 3 PASS bar tightened mid-arc with no justification

From `findings/cfr-phase2.md:252-254`:
> *"Pre-registered Phase 3 cut: deep CFR mean Sharpe >= Phase 1 + 0.15 AND
> CFR > naive uniform by >= +0.10. The +0.15 over Phase 1 (vs +0.10 in
> Phase 2)..."*

Phase 2's cut was "Phase 1 + 0.10"; Phase 3's was "Phase 1 + 0.15". **The bar

Phase 3 missed by +0.021 mean lift; under the Phase 2 cut (Phase 1 + 0.10)

## 4. Right metric, wrong question

### 4a. `apps/gate` — drawdown forecaster measured on Sharpe

`apps/gate` is documented in `CLAUDE.md` as "aggregate drawdown forecaster as
an EW-exposure gate". Its purpose is to **reduce drawdowns**. The eval
script (`apps/gate/scripts/run_walkforward.py:213`) verdicts on `mean_alpha`
of *Sharpe*. **A gate that prevents one 30% drawdown but adds 0.15 of
trade-cost friction in calm periods may be Sharpe-flat but max-DD-positive
and totally deployable as a risk overlay.** None of the gate finding's
tables show max DD, CVaR, or Sortino comparisons (`gate-drawdown-v0.md`,
section "Canonical arm" — only `avg exp`, `unc Sh`, `gated Sh`, `alpha`).
The package code has `max_drawdown`, `sortino`, `calmar` defined in
`packages/portfolio/src/ss_portfolio/metrics.py:39,48,58` — they're imported
in some apps and **never used in any verdict-making**. The verdict
framework forced the gate strategy to be evaluated on the wrong axis.

### 4b. `apps/vol` — vol surface predictor measured on per-cell Sharpe

`findings/vol-surface-v0.md:233-238` admits the per-cell Sharpe metric is
"a weak metric — no temporal aggregation, no annualization. The honest
portfolio Sharpe over per-rebal aggregated PnL was never computed." It
then verdicts the strategy `inconclusive` on the basis of being 0.011
below the +0.10 threshold *on the admittedly-weak metric*. **The metric
problem and the threshold are independent failure modes that compound;
either alone would justify "go compute the right metric"; together they
produce a verdict that's actively misleading.** Vol's 5/5 directional
consistency — the strongest single-axis signal in the repo — got benched
because of a metric the doc itself flags as wrong.

### 4c. `apps/pairs` — pair-spread mean reversion measured on Sharpe vs zero

Pair trading is structurally a dollar-neutral relative-value strategy; its
*market beta is zero by construction*. Reporting Sharpe vs a zero-return
benchmark is correct, but using the same Sharpe thresholds as long-only
strategies (which carry universe beta) implicitly demands that pairs *beat
universe beta + alpha*, when its actual claim is just "alpha exists". The
finding (`pairs-classical-v0.md`) doesn't report CVaR, max DD, or Sortino
on the dollar-neutral PnL — which are the natural metrics for a strategy
whose value proposition is "uncorrelated to broad market".

### 4d. The leaderboard schema has only Sharpe and IC

`leaderboard.md:74` schema:
```
| date | app | experiment | universe | windowing | metric | train | val | delta | verdict | artifact |
```

The `metric` column accommodates anything, but in practice every row uses
mean val Sharpe, mean val IC, or mean val Pearson r. Across **all 50+
rows** I can see in the leaderboard, **zero rows report max DD, CVaR, or
Sortino in the `val` column**. The schema doesn't forbid it; the *culture*
of the doc doesn't include it.

### 4e. `apps/regime` celebrates Sharpe 0.63 vs EW Sharpe 1.26

`findings/regime-baselines.md:23,34` literally shows the regime app's
canonical baseline at Sharpe **+0.63** vs equal-weight on the same universe
at Sharpe **+1.26** — i.e. **alpha = -0.63, the worst single number in
the repo** — and the page treats this as a baseline to improve upon, not as a
falsification of the strategy. The "improvement vs the regime baseline"
metric is then used for every subsequent CWT scoring decision in the arc.
This isn't a threshold problem per se, but it is a metric problem: *what
the entire regime arc measures (improvement vs its own baseline)* and what
the deployability question demands (alpha vs passive EW) are different
quantities, and only the latter is load-bearing.

## 5. Recommended standardization

The current framework is **performative compliance with no actual decision
power**: it produces 6 verdict labels backed by 5 different deployment
thresholds, and the labels routinely flip on a single-percent boundary check
or on a denominator misframing. Replace it.

### 5a. Replace the verdict-label tier with a 2-class decision + a confidence interval

The current 6-label vocabulary collapses naturally to 2 actions: **deploy
(or paper-trade)** vs **don't deploy (research-only)**. Everything in
between is theater. Replace with:

- **`deploy-eligible`** — the strategy clears its primary AND secondary
  metric thresholds with 95% bootstrap CI lower bound > 0.
- **`research`** — anything else.

The `confirmed-OOS / reversed-OOS / partial-OOS / confirmed-null` distinction
is descriptively useful but adds no operational power; collapse them into the
prose of the findings page where they belong.

### 5b. Define a primary + secondary metric mapping by strategy class

The strategies in this repo split into 4 structurally distinct classes; pick
metrics for each:

| Strategy class | Examples | Primary metric | Secondary metric |
|---|---|---|---|
| **Long-only allocator** | regime, relational, factor-as-portfolio, DCA, CFR Phase 4d | `mean alpha vs passive EW` (Sharpe units) | `worst-window Sharpe - passive EW Sharpe` |
| **Drawdown / risk overlay** | gate, any future macro meta-gate | `max DD reduction vs ungated` (absolute %) | `CVaR_05 reduction vs ungated` |
| **Dollar-neutral relative value** | pairs, factor long-short | `Sortino vs zero` | `worst-window Sortino` |
| **Prediction-only model (no portfolio claim)** | factor rank-IC head, sizing-input v0, vol surface as a predictor | `mean val IC` (or Pearson r) | `lag-1 autocorr of per-window signal-quality` (already used in factor-sizing-input) |

Within each class **the primary metric threshold should be**:

- **Long-only**: alpha vs EW >= +0.15 AND bootstrap CI lower bound > 0 across
  windows. **Anchor this in one place** (e.g. `passive-ew-benchmark.md`) and
  forbid other findings from re-defining it.
- **Drawdown overlay**: max DD reduction >= +20% relative AND ungated-Sharpe-cost
  <= 0.1 absolute (i.e., flatting must save real tail without destroying calm-period
  return).
- **Dollar-neutral**: Sortino >= +0.5 with bootstrap CI lower bound > 0 (Sortino
  not Sharpe because pair-spread vol is naturally noisier on the upside).
- **Prediction**: val IC mean >= +0.01 AND positive in >= 5/n windows. Promotion
  to portfolio-level requires re-evaluation under the long-only class.

### 5c. Replace point-estimate thresholds with bootstrap confidence intervals

Every verdict must report a 95% bootstrap CI on the primary metric. **A
strategy is `deploy-eligible` only if the CI lower bound is strictly above
the threshold.** This kills the entire "+0.099 vs +0.20 fails by single
percent" theater — instead the question becomes "is the CI lower bound
clearly positive?", which is robust to the threshold choice.

With n=5-6 walk-forward windows, bootstrap CIs will be wide. **That's the
point.** Right now the framework presents single-point estimates as if they
were precise; the bootstrap forces the discussion to honestly grapple with
the fact that nothing in the repo has been measured well enough to support a
single-percent decision boundary.

### 5d. Leaderboard schema under this proposal

```
| date | app | experiment | universe | windowing | class | primary metric (val) | 95% CI | secondary metric (val) | passive EW comparator | deploy-eligible? | artifact |
```

Two changes from current: add `class` (long-only / overlay / dollar-neutral /
prediction), add `95% CI` next to the primary metric, add explicit
`passive EW comparator` and `deploy-eligible?` columns. Drop the verdict
vocabulary; the `deploy-eligible?` boolean replaces it.

### 5e. Forbid mid-arc threshold revision

`findings/cfr-phase2.md:254` raises the PASS bar from "Phase 1 + 0.10" to
"Phase 1 + 0.15" between phases. **A rule: pre-registered cuts can be
written once; they can be questioned but not silently revised within an
arc.** If a new cut is genuinely needed, it goes in a new pre-reg with a
sourced argument, not a re-write of the existing one.

### Operational rules in CLAUDE.md that would need re-derivation

About **half the "Operational rules extracted from findings"** section of
CLAUDE.md uses a numeric threshold to anchor the rule (e.g. "mean val IC
below ~+0.02", "+0.10 deployment threshold", "alpha vs EW positive but
below +0.15", "+0.215 z lift"). Under the new framework each of those
needs to either:
1. Cite the bootstrap CI rather than the point estimate, or
2. Be reclassified as "qualitative observation, not threshold-based".

Most would survive — the *direction* of every rule is correct — but each
would need to be reframed to acknowledge "CI lower bound did/didn't cross
the threshold" rather than "point estimate did/didn't".

### What wouldn't change

The risk-rail thresholds (max_position, max_data_age, drift_threshold,
kill-switch) are calibration choices that don't propagate into verdicts;
they stay. The 6-window walk-forward structure stays (it's the n that's
the problem; widening to more bootstrap samples is mechanically possible
but isn't actually fixing the underlying n=6 power problem either). The
indicator / wavelet / portfolio package code is unaffected — the
proposal only restructures the *decision* layer.
